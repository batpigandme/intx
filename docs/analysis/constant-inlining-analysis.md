# Constant Inlining & Scoping Analysis on `limb16-pipeline-imul-all`

> **An empirical and disassembled machine-code investigation into how V8 TurboFan inlines literals, module constants, local constants, cached functions, and imported modular helpers in wide integer multiplication.**

---

## 1. Executive Summary & Objective

In high-performance JavaScript arithmetic, a recurring design question is:
> *Does defining constants at module scope (`const LOW_16 = 0xffff`), local scope, inline literals (`& 0xffff`), cached method references (`const imul = Math.imul`), or imported module helpers (`const mul = require('./mul')`) impact TurboFan's optimization pipeline, register allocation, or generated machine assembly?*

To answer this, we conducted an empirical disassembly and benchmark study using the best-performing wide multiplication kernel: **`limb16-pipeline-imul-all`**.

## 2. The 5 Evaluated Variations

```javascript
// 1. Literal Variant (pipe-literal)
function wmul_literal(a, b, out) {
  const al = a & 0xffff, ah = a >>> 16;
  const bl = b & 0xffff, bh = b >>> 16;
  const albl = Math.imul(al, bl) >>> 0;
  const llh = albl >>> 16;
  const ahbl = (Math.imul(ah, bl) + llh) >>> 0;
  const hll = ahbl & 0xffff;
  const hlh = ahbl >>> 16;
  const albh = (Math.imul(al, bh) + hll) >>> 0;
  const lhh = albh >>> 16;
  out[0] = (Math.imul(ah, bh) + hlh + lhh) >>> 0;
  out[1] = Math.imul(a, b) >>> 0;
  return out;
}

// 2. Module-Scoped Constant (pipe-module-const)
const MODULE_LOW_16 = 0xffff;
function wmul_module_const(a, b, out) {
  const al = a & MODULE_LOW_16, ah = a >>> 16;
  // ... rest identical
}

// 3. Local-Scoped Constant (pipe-local-const)
function wmul_local_const(a, b, out) {
  const LOCAL_LOW_16 = 0xffff;
  const al = a & LOCAL_LOW_16, ah = a >>> 16;
  // ... rest identical
}

// 4. Cached Math.imul (pipe-cached-imul)
const imul = Math.imul;
function wmul_cached(a, b, out) {
  const al = a & 0xffff, ah = a >>> 16;
  const albl = imul(al, bl) >>> 0;
  // ... rest identical
}

// 5. Imported Helper (pipe-imported-mul)
const mul = require('../../mul'); // Math.imul(a, b) >>> 0
function wmul_import(a, b, out) {
  const al = a & 0xffff, ah = a >>> 16;
  const albl = mul(al, bl);
  // ... rest identical
}
```

## 4. Key Compiler Insights & Proofs

### 1. `literal` vs `module-const` Produce 100% Byte-for-Byte Identical Assembly
Comparing [`asm/out/v24.19.0/literal.txt`](../../asm/out/v24.19.0/literal.txt) and [`asm/out/v24.19.0/module-const.txt`](../../asm/out/v24.19.0/module-const.txt) confirms:
- Both compile to an identical **480 bytes** of machine code.
- In both cases, TurboFan's `ConstantFolding` and `SimplifiedLowering` pass recognize `& 0xffff` (or `& MODULE_LOW_16`) as a 16-bit mask and lower it to a hardware **`movzxwl`** (move with zero-extension) instruction.
- **There is zero memory load or runtime overhead for module-scoped constants.**

### 2. `Math.imul` Inlines to Single-Cycle `imull`
All 5 multiplications in the pipelined carry chain:
- `al * bl` $\to$ `imull %r12d, %r9d`
- `ah * bl` $\to$ `imull %r9d, %r15d`
- `al * bh` $\to$ `imull %r11d, %r12d`
- `ah * bh` $\to$ `imull %r12d, %r15d`
- `a * b` $\to$ `imull %edi, %edx`

are compiled directly into hardware ALU instructions without any function calls or floating-point conversions.

### 3. Modular Function Inlining (`pipe-imported-mul`)
In [`asm/out/v24.19.0/import.txt`](../../asm/out/v24.19.0/import.txt), TurboFan completely eliminated the `mul(a, b)` function call frame during the `InlinerPhase`, splicing the identical `imull` sequence directly into the body of `wmul`.

---

## 5. Summary Recommendation

- Whether using `0xffff` literals, module-level `const LOW_16 = 0xffff`, or imported modular helpers `mul(a, b)`, **V8 TurboFan compiles all variations down to the exact same optimal x86-64 machine instructions**.
- Developers can freely choose the most readable, maintainable, and modular code style without sacrificing a single cycle of CPU performance.
