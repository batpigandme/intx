# The Node 24 vs Node 26 gap: two rows, two different things

**Box: `boxA`, boot 2.** Same CPU model as the original `boxA` runs (Intel Xeon @ 2.10GHz, family 6 model 207
stepping 2, 4 cores, no `cpu` event source), but the container rebooted at 00:57Z, after the original blocks
(00:06–00:37Z). Everything measured here is from boot 2. It's compared against boot-1 figures only as a separate
observation, never pooled with them. Record: [`data-boxA/node24-gap/boot2-record.txt`](data-boxA/node24-gap/boot2-record.txt).

## Verdict

**The two rows aren't the same effect, and they share no code property.** One is a real V8 difference; the other is a
harness-order effect that moves too much to pin down.

- **`i32.add` showdown, "Inline Operator": real.** It reproduces on stock `a8de2d6`, on all three boxes (two CPU
  models), in all four blocks, in either suite position, and in a standalone script with no intx code. It is
  **not a Node 24 regression**: Node 22.22.2 is just as slow (5.73–6.03 ns). Node 26.7.0 is the one that changed
  (0.43–0.47 ns). **What differs:** for `acc = ((acc | 0) + c) | 0`, with `c` a closure variable and the loop first
  reached through on-stack replacement, V8 12.4 and 13.6 emit TurboFan code that does the add in **Float64**. Each
  iteration converts `acc` from int32 to double (`vcvtlsi2sd`), adds (`vaddsd`), and converts back (`vcvttsd2siq` plus
  an overflow check). V8 14.6 truncates `c` to int32 once, before the loop, and the loop body is one `addl`. No deopt
  on any version. Coercing `c` in the source (`(c | 0)`) removes the gap on every version. **Node 26's fix covers `+` only:** the same loop with `-` is still slow on Node 26 (5.50–5.59 ns; boxD follow-up below).
- **Patched exploration 06, first row: position, not code, and not the fallback.** It reproduces on the stock
  wall-clock harness with no fallback module loaded, so it isn't a patch artifact. But it follows **whichever runner is
  first** in that suite, on **Node 24 only**: Node 22 and 26 are clean. The row is fine when moved last (0.89 ns), and
  the runner that replaces it in first place slows down instead. Its median moves a lot between blocks, 1.83, 3.58 and
  5.43 ns on boot 2 and 5.56–5.66 ns on boot 1, while its peak stays at 0.78–0.86 ns on boot 2: most samples are slow, some
  aren't. A ratio that moves this much between blocks can't be pinned to one mechanism, so the investigation of this row stops here, without
  a mechanism.

## §1. Stock first

The "Inline Operator" row comes from `src/i32/add/showdown.js`, which uses the stock wall-clock `bench.suite`. It was
never touched by the patch.

Exploration 06 is PMU-gated on stock, so its first-row number existed only under the patched branch's fallback. To
take the patch out of it, [`scratch/a-06-stock-timer.js`](data-boxA/node24-gap/scratch/a-06-stock-timer.js) is a copy
of 06 in a scratch directory. It changes only the harness call, from `cycles.bench.suite` to the stock
`bench.suite`, with the options the fallback would pass (`rounds: 1e3`, `pause: 0`, `dur: 10`). It ran against a
pristine `git archive` of `a8de2d6` with no `fallback.js` in the tree. The first row is still slow on Node 24, so the
effect isn't about the patch.

## §3. Localize

The rows looked alike only because both are slow on Node 24. They differ in every way that matters:

| | "Inline Operator" | 06 first row |
|---|---|---|
| Follows the code or the position? | Code (slow first or last) | Position (fine when last; the new first runner slows) |
| Node 22 | Slow | Clean |
| Stable across blocks? | Yes, ±3% | No: 1.8–5.7 ns |
| Peak vs median | Peak is also slow | Peak is fast, median slow |

The "Inline Operator" loop is identical to exploration 01's `[TRAP]` row: same `c`, same context, same loop body. Yet
01's row ran at 0.44 ns on Node 24 under the fallback. The difference is calling pattern. The `i32.add` showdown passes
`iters: 1e8`, so the runner's first call spends all 1e8 iterations in one invocation and is optimized through OSR.
01's dynamic calibration first calls the runner many times with small counts.

The reduction reproduces this without intx. [`scratch/reduce.js`](data-boxA/node24-gap/scratch/reduce.js) builds the
kernel the way `createRunner` does (a `new Function` factory whose parameters become closure variables) and times five
calls of 1e8 with `performance.now()`. Medians, ns per iteration, boot 2:

| Variant | Node 22.22.2 | Node 24.19.0 | Node 26.7.0 |
|---|---:|---:|---:|
| `((acc\|0) + c)\|0`, cold, 5 × 1e8 (block 3 / 4) | 5.82 / 5.92 | 5.96 / 5.78 | 0.45 / 0.44 |
| same, after 2000 warm-up calls of 1e4 | 5.70 / 0.71 | 0.46 / 0.43 | 0.44 / 0.45 |
| `((acc\|0) + (c\|0))\|0`, cold, 5 × 1e8 | 0.71 / 0.69 | 0.46 / 0.45 | 0.44 / 0.44 |

The slowness persists across all five calls, not just the first. Warming up first rescues Node 24 in both blocks, and
Node 22 in one of two. Node 22's 0.7 ns floor is the same for the coerced form, so it's a general Node 22 loop-cost
difference, not part of this effect.

## §4. Diagnose

All diagnostics ran in separate, untimed processes on `reduce.js uncoerced big`. Raw files in
[`data-boxA/node24-gap/diag/`](data-boxA/node24-gap/diag/trace-opt-verbose-deopt-node24.19.0.txt).

**No deopt loop.** `--trace-opt-verbose --trace-deopt` shows the same sequence for `kernel` on Node 24 and 26: Maglev
OSR, then TurboFan OSR. The only bailout is `deopt-eager, reason: prepare for on stack replacement (OSR)`, the routine
hand-off from Maglev to TurboFan, on both. Node 22 has no Maglev tier by default and goes straight to TurboFan. No
version shows a non-OSR deopt.

**The generated code differs.** `--print-opt-code --print-opt-code-filter=kernel`, one unrolled step of the loop:

Node 24.19.0 (V8 13.6): `acc` goes int32 → double → int32 on every iteration, and `c` sits in `xmm0` as a double.

```
vcvtlsi2sd xmm1,xmm15,rdx      ; acc (int32) -> double
vaddsd     xmm1,xmm1,xmm0      ; + c, as Float64
...
vcvttsd2siq rdx,xmm1           ; double -> int (the | 0)
cmpq rdx,0x1 / jo ...          ; out-of-range check, slow path to DoubleToI
movl rdx,rdx
```

Node 26.7.0 (V8 14.6): `c` is truncated to int32 in `r12` once, outside the loop (the only two `vcvttsd2siq` in the
function are there), and the loop is integer-only.

```
addl rdx,r12                   ; acc += c, int32
```

| | `vaddsd` in function | `vcvttsd2siq` in function | Code size |
|---|---:|---:|---:|
| Node 22.22.2 | 2 | 2 | 668 B |
| Node 24.19.0 | 5 (one peeled iteration plus a 4× unrolled loop) | 5 | 936 B |
| Node 26.7.0 | 0 | 2 (pre-loop, for `c`) | 740 B |

Node 24's loop-carried dependency runs through `vcvtlsi2sd` → `vaddsd` → `vcvttsd2siq` on every iteration, where
Node 26's is one `addl`. The ~5.3 ns difference is consistent with the length of that chain at 2.1 GHz. That last point
is an inference from latencies; nothing here measured cycles, since this box has no PMU. **This is where the
investigation stops:** what differs is that V8 14.6 narrows `acc + c` to a Word32 add when the result is truncated with
`| 0` and `c` is a closure variable, and V8 12.4 and 13.6 don't in this OSR compile. (For `-`, V8 14.6 doesn't either: 5.50–5.59 ns on Node 26, boxD follow-up below.) Which V8 change did that wasn't
looked for.

## What this means for the benchmark numbers already recorded

- The "Inline Operator" row is a **baseline** in Abdul's `i32.add` showdown. On Node 22 and 24, in this calling
  pattern, it measures the Float64 path, not the inline integer add it's labelled as. That's a fact about the harness
  row, not about `i32.add`: the `add(acc, c)` rows coerce inside the function and are fast on every version.
- 06's first-row figures on Node 24 (boot 1 patched runs, boot 2 stock scratch) **shouldn't be read as a property of
  "Read-Only Baseline"**. Moved last, the same runner gives 0.89 ns.
- Nothing in Abdul's code was changed. Scratch copies live in
  [`data-boxA/node24-gap/scratch/`](data-boxA/node24-gap/scratch/reduce.js). The repeat-block driver is
  [`scratch/runrep.sh`](data-boxA/node24-gap/scratch/runrep.sh), and its log is
  [`runlog.txt`](data-boxA/node24-gap/runlog.txt).

## Follow-up on boxD: `--no-use-osr`, the form of `c`, and the operator

**This ran on a different box.** The session resumed on an Intel Xeon @ 2.80GHz, family 6 **model 85** stepping 7
(Cascade Lake), not `boxA`'s model 207, so it's labelled **`boxD`**. It's the same CPU model as `boxC`, but a
different container and session, so it's reported separately. Nothing below is compared with `boxA`'s numbers as if
it came from the same machine. Record:
[`data-boxD/node24-gap-followup/box-record.txt`](data-boxD/node24-gap-followup/box-record.txt).

All three checks use [`reduce.js`](data-boxD/node24-gap-followup/reduce.js), the same scratch script as above. It gains
two optional arguments, the form of `c` and the operator; with neither given, it behaves exactly as before. Calls are
cold (1 untimed + 5 timed calls of 1e8) unless marked. Node 22.22.2, 24.19.0 and 26.7.0, two blocks, one process at a
time. Raw output: [`data-boxD/node24-gap-followup/`](data-boxD/node24-gap-followup/runlog.txt).

### Baseline first: it lands where `boxC` did

`boxC`, also Cascade Lake, measured the showdown's "Inline Operator" row at 180.6 M/s (5.54 ns) on Node 24 against
1.88 B/s (0.53 ns) on Node 26. On `boxD` the reduction gives, in ns per iteration, block 1 / block 2:

| Form | Node 22.22.2 | Node 24.19.0 | Node 26.7.0 |
|---|---:|---:|---:|
| uncoerced `c`, cold | 5.73 / 5.56 | 5.71 / 5.63 | 0.56 / 0.54 |
| uncoerced `c`, warmed | 0.61 / 0.62 | 0.46 / 0.46 | 0.46 / 0.50 |
| `(c \| 0)`, cold | 0.61 / 0.64 | 0.54 / 0.54 | 0.54 / 0.54 |
| literal, cold | 0.61 / 0.61 | 0.46 / 0.53 | 0.47 / 0.46 |

So the gap reproduces on `boxD`, at the same size as on `boxC`. (Node 26's block 1 cold run had one slow first timed
call, 5.39 ns, before settling at 0.53–0.57.)

### 1. `--no-use-osr`: OSR is the cause, not a correlate

Per-call times, since the median hides the shape. Node 24.19.0, cold, with the flag:

| | Call 1 | Call 2 | Call 3 | Call 4 | Call 5 |
|---|---:|---:|---:|---:|---:|
| uncoerced `c`, block 1 | 14.96 | 12.52 | 13.55 | 5.88 | **0.50** |
| uncoerced `c`, block 2 | 12.85 | 12.66 | 12.58 | 5.85 | **0.48** |
| `(c \| 0)`, block 1 | 16.05 | 15.04 | 14.50 | 5.89 | **0.47** |
| `(c \| 0)`, block 2 | 15.75 | 15.77 | 16.06 | 5.85 | **0.48** |

With OSR off, the long first calls run in unoptimized code (12–16 ns, the same for both forms). Once the regular
compile is in use, **the uncoerced form runs as fast as the coerced one**: 0.48–0.50 ns against 0.47–0.48. The ~5.7 ns
code never appears. Node 22 shows the same (0.61–0.64 ns from call 4), and so does Node 26 (0.46–0.50 ns in call 5).
Call 4's ~5.9 ns is identical for both forms on 24 and 26, so it's an intermediate tier rather than this effect; it
wasn't investigated. **So the slow code is specific to the OSR compile, and disabling OSR removes the gap.**

### 2. Does `c` have to be a closure variable? No

Cold, uncoerced `+`, block 1 / block 2:

| Where `c` comes from | Node 22.22.2 | Node 24.19.0 | Node 26.7.0 |
|---|---:|---:|---:|
| closure variable (as in intx) | 5.73 / 5.56 | 5.71 / 5.63 | 0.56 / 0.54 |
| local, `const cl = -1640531527` inside the kernel | 5.58 / 5.64 | 5.58 / 5.75 | 0.54 / 0.55 |
| local copied from the closure, `const cl = c` | 5.63 / 5.61 | 5.61 / 5.60 | 0.61 / 0.55 |
| parameter of the kernel | 5.64 / 5.69 | 5.81 / 5.60 | 0.53 / 0.53 |
| the literal written into the expression | 0.61 / 0.61 | 0.46 / 0.53 | 0.47 / 0.46 |

**Every named form is slow on Node 22 and 24**, including a local initialized from a literal a line above the loop.
Only the literal written directly into the expression is fast. So this isn't about closure variables. It's about a
value that reaches the loop through a variable, which the OSR code then treats as unknown. That fits OSR entering
mid-loop and taking its values from the unoptimized frame, but that last step is an inference; it wasn't traced.

### 3. Is it just `+`? No: `-` too, and on Node 26 `-` is still slow

Cold, block 1 / block 2, `acc = ((acc | 0) OP c) | 0` against `acc = ((acc | 0) OP (c | 0)) | 0`:

| Operator | Form | Node 22.22.2 | Node 24.19.0 | Node 26.7.0 |
|---|---|---:|---:|---:|
| `+` | uncoerced | 5.73 / 5.56 | 5.71 / 5.63 | **0.56 / 0.54** |
| | coerced | 0.61 / 0.64 | 0.54 / 0.54 | 0.54 / 0.54 |
| `-` | uncoerced | 5.76 / 5.61 | 5.63 / 5.57 | **5.50 / 5.59** |
| | coerced | 0.63 / 0.64 | 0.53 / 0.54 | 0.53 / 0.55 |
| `^` | uncoerced | 0.76 / 0.73 | 0.55 / 0.54 | 0.55 / 0.54 |
| | coerced | 0.74 / 0.73 | 0.55 / 0.54 | 0.53 / 0.55 |
| `*` | uncoerced | 5.80 / 5.62 | 5.51 / 5.65 | 5.54 / 5.84 |
| | coerced | 5.62 / 5.66 | 5.88 / 5.54 | 5.59 / 5.66 |

- **`^` is fast in every form on every version.** A bitwise operator converts both operands to int32 itself, so
  there's no add whose representation needs working out.
- **`-` behaves like `+` on Node 22 and 24, and stays slow on Node 26.** So the Node 26 improvement covers `+` and not
  `-`. The earlier statement that Node 26 "fixed" this should be read as "fixed it for `+`".
- **`*` doesn't answer the question.** It's slow even coerced, on every version. That's expected, not this effect:
  `(a * b) | 0` has to multiply in floating point, because the product of two int32s can exceed 2^53. The int32
  multiply is `Math.imul`.

Taken together: the int32 truncation from the outer `| 0` reaches the add in the regular compile, and on Node 26's OSR
compile for `+`, but not for `-` there, and not for either on Node 22 or 24. Where exactly V8 does or doesn't infer it
wasn't pursued.
