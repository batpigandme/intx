# Does the cold-call pattern explain more than one showdown row?

**Box: `boxA`, boot 3.** Same CPU model as before (Intel Xeon @ 2.10GHz, family 6 model 207 stepping 2, 4 cores, no
`cpu` event source), but the container rebooted again, at 02:01Z. Nothing here is pooled with boot 1 or boot 2.

## Verdict

**It's one row.** Across all 60 rows of the five `showdown.js` files, on stock `a8de2d6`, exactly **one** row is more
than 2× slower when called cold (the way the showdown harness calls it) than when warmed with small calls first, in
both blocks: the `i32.add` "Inline Operator" row. It's slow on Node 22.22.2 (8.2–8.5×) and 24.19.0 (12.9–13.1×), and
not on 26.7.0 (0.97–0.99×). Every mulhi and mulwide candidate sits between 0.91× and 1.07× in every block on every version. The pre-26 OSR effect
doesn't make the showdown harness unreliable in general; it hits one row whose loop reads an uncoerced closure
variable. No showdown row does this with `-`, which Node 26 did **not** fix (5.50–5.59 ns on boxD; see [`node24-gap-2026-09-25.md`](node24-gap-2026-09-25.md)).

Two smaller things, recorded and not chased:

- **Five rows in `src/i32/showdown.js` (div, mod, divmod, rotl, rotr) are 1.4–1.9× slower cold on every version,
  Node 26 included.** Because Node 26 shows it too, it isn't the pre-26 effect. It's some version-independent
  difference between the two calling patterns at that file's `iters: 1e7`.
- **One cell crossed 2× in one block only:** `i32` divmod on Node 24, 2.14× in block 2 and 1.37× in block 1. A single
  block isn't a finding.
- **One row is faster cold:** `i32.add` "Parallel 4x" on Node 24, 0.73–0.77×.

## Method

- **Rows.** [`scratch/`](data-boxA/osr-sweep/scratch/osr.js) holds a copy of each `showdown.js`, identical except
  that the final `bench.suite` / `bench.suite.rank` call is replaced by `module.exports = { runners, iters }`. The
  runners are Abdul's own `createRunner` output, and each file's own `iters` (2e7 for `i32/mul`, 1e8 for `i32/add`,
  1e7 for the rest) is kept.
- **Cold** is what microbe's fixed-`iters` suite does per runner: one untimed call of `iters` (the harness's warm-up),
  then five timed calls of `iters`. **Warm** first makes 2000 untimed calls of 1e4, then does exactly the same.
- **Timing** uses the runner's own `tic`/`toc`, backed by `performance.now()`, around its loop. Each cell is the median
  of the five timed calls, in ns per iteration.
- **Isolation.** One row, one pattern, one Node version per process, run one after another with nothing else on the box.
  Two blocks, each a full pass over 60 rows × 2 patterns × 3 Node versions. No natives syntax, no `node -e`.
- **Why a driver and not the harness:** the stock harness only has the cold pattern, so warming has to happen before
  it. Calling the runner directly keeps everything else identical.
- **Data:** [`data-boxA/osr-sweep/`](data-boxA/osr-sweep/runlog.txt), one JSONL per block and Node version, with all
  five per-call timings kept.

## What "ratio" means here

Cold ÷ warm, per block. A ratio above 1 means the harness's own calling pattern measured the row as slower than it
runs once warmed. The ratio is only as meaningful as its denominator: the one flagged row costs ~0.45 ns warm on
Node 24, so its 13× is about 5.3 ns of extra time per iteration.
